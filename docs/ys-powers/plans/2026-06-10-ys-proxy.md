# ys-proxy & Trace Viewer 实施计划

## 1. 概述

**目标**：在 cc-switch-tui 中集成 API 代理与 Trace 查看功能，实现 `ys-proxy cl-kimi` → 本地代理 → 上游 Provider → 记录 Trace → Web 前端查看 的完整链路。

**技术栈**：
- 后端：Rust (axum + tokio + reqwest + rusqlite)
- 前端：React + TypeScript + Tailwind CSS + tanstack-query
- 参考实现：claude-tap (Python + aiohttp)

**分支**：`feat/ys-proxy`

### 关键依赖关系

| 组件 | 依赖 | 说明 |
|------|------|------|
| `proxy::handler` | `proxy::upstream`, `proxy::filter`, `trace::store` | handler 协调上游请求、header 过滤、trace 记录 |
| `proxy::upstream` | `proxy::sse` | upstream 返回的 Stream 交给 SseParser 解析 |
| `api::traces` | `trace::store` | 查询 API 直接操作 trace DB |
| `trace::store` | `trace::models` | 数据结构定义 |
| `shell.rs` | 无（纯字符串生成） | 生成 `ys-proxy` wrapper function |
| 前端 Dashboard | `api::traces` (GET /api/traces/sessions) | 展示 session 列表 |
| 前端 Viewer | `api::traces` (GET /api/traces/sessions/:id/records) | 展示 record 详情 |

### Slice 2: SSE 流式代理

**Slice 目标**：实现 SSE 边转发边解析，Claude Code 能实时接收流，前端能查看 message 内容。

#### 任务 2.1: proxy::sse（SseParser）

**描述**：实现 SSE 字节流解析器，参考 claude-tap 的 `SSEReassembler`。

**实现内容**：
- `SseParser` struct
- `feed_bytes(chunk: Bytes)` — 消费字节流
- 解析 `event:`、`data:`、空行，提取完整 event
- 将 event 转换为 `SseEvent { event_type, data }`
- 处理 `[DONE]` 终止符

**核心状态机**：
```
收到 bytes → 按 \n 分割 → 逐行处理
  event: xxx → 记录 event_type
  data: xxx  → 累积 data 行
  空行       → 输出一个完整 SseEvent
```

**验收标准**：
- 能正确解析单 chunk 内的完整 event
- 能正确处理跨 chunk 的 event（数据被分割到多个 TCP packet）
- 能正确处理 `[DONE]`
- 单元测试覆盖边界情况

**验证步骤**：
```bash
cargo test proxy::sse
```

**工作量**：L（3 小时）
**依赖**：0.2

#### 任务 2.2: proxy::upstream 升级（Stream 分流）

**描述**：将 upstream 从"缓冲完整响应"升级为"流式转发 + 旁路解析"。

**实现内容**：
- `forward_streaming(request, upstream_url, api_key)` 方法
- 使用 `reqwest::Response::bytes_stream()` 获取 Stream
- 使用 `tokio::sync::broadcast` 或 `flume` 将 Stream 分发给两个 consumer：
  1. axum response（写给 Claude Code）
  2. SseParser（解析事件）
- 或者：用 `futures::stream::StreamExt::map` 在转发的同时解析

**关键技术决策**：
- **方案 A**：`tokio::sync::broadcast` — 简单但 consumer 必须实时消费
- **方案 B**：自定义 Stream，每次 poll 时同时 write 到 response body 和 feed parser
- **推荐 B**：更可靠，不依赖 consumer 速度

**验收标准**：
- Claude Code 接收到的流不被缓冲（逐 chunk 到达）
- parser 能同步消费相同的 chunk
- 即使 parser panic，转发不受影响

**验证步骤**：
```bash
# 集成测试：模拟上游 SSE，验证下游收到的 chunk 顺序和时序
cargo test proxy::upstream::test_streaming
```

**工作量**：L（4 小时）
**依赖**：2.1

#### 任务 2.3: proxy::handler 升级（流式响应）

**描述**：修改 handler，对流式请求使用新的 upstream API。

**实现内容**：
- 检测请求是否要求 SSE（`accept: text/event-stream`）
- SSE 请求走 `forward_streaming`
- 非 SSE 请求继续走原来的 `forward`（缓冲模式）
- handler 启动一个后台 task：
  - 消费 parser 输出的 event
  - 累加到 snapshot
  - 定期（或 event 结束时）将 snapshot 写入 trace store

**Session 生命周期**：
```
收到请求 → create_session → 转发请求
  ↓
收到 response headers → 开始流式转发
  ↓
每个 SSE event → feed parser → 更新 snapshot
  ↓
流结束 → 将最终 snapshot 作为 record 写入 → finalize_session
```

**验收标准**：
- SSE 请求边转发边记录
- 非 SSE 请求继续正常工作
- trace store 中有完整的 response record（snapshot）

**验证步骤**：
```bash

cargo run

# 2. 发送 SSE 请求
curl -N -X POST http://localhost:7480/ys-proxy/cl-kimi/v1/messages \
```

## 5. 风险与缓解

| 风险 | 阶段 | 影响 | 缓解措施 |
|------|------|------|----------|
| SSE Stream 分流实现复杂，阻塞 Slice 2 | 2.2 | 高 | 先实现最简单方案（手动 Stream impl），保证 Claude Code 能工作，再优化性能 |
| `reqwest` + `axum` 流式 body 类型不兼容 | 2.2 | 高 | 提前做技术预研（PoC），用 `bytes::Bytes` 作为桥梁 |
| 前端组件与真实数据结构 mismatch | 3.3 | 中 | Slice 1 就要求端到端验证，前端始终对接真实 API |
| SQLite 并发写入冲突 | 1.1 | 低 | TraceStore 使用独立 DB 文件 + WAL 模式，单 writer task |
| upstream API 格式突变 | 3.1 | 低 | parser 只解析已知字段，未知字段放入 `extra: Value` 透传 |
